# เอกสารออกแบบระบบ — บัญชีบ้านเรา

## 1. โจทย์และขอบเขต

**โจทย์:** ทำบัญชีรับ-จ่ายของครอบครัว 4 คน ใช้ได้จากทุกที่ทุกอุปกรณ์ ข้อมูลอยู่บนคลาวด์

**สิ่งที่ต้องได้:**
- ทุกคนบันทึกจากเครื่องตัวเองแล้วเห็นข้อมูลชุดเดียวกัน ไม่ต้องส่งไฟล์หากัน
- บันทึกได้เร็ว (เปิดแอป → พิมพ์ตัวเลข → เลือกหมวด → เสร็จ ภายใน 10 วินาที)
- ดูได้ว่าเดือนนี้ใช้ไปเท่าไหร่ หมดกับอะไร ใครใช้ และเหลือเท่าไหร่
- ไม่มีค่าใช้จ่ายรายเดือน และไม่ต้องมีคนคอยดูแลเซิร์ฟเวอร์

**สิ่งที่ไม่ทำในเวอร์ชันนี้** (ตั้งใจตัดออก เพราะเป็นบัญชีในบ้าน ไม่ใช่บัญชีบริษัท)
- ระบบบัญชีคู่ (debit/credit), งบดุล, ภาษี, ใบกำกับภาษี
- การอ่านสลิปอัตโนมัติ / เชื่อม API ธนาคาร
- หลายสกุลเงิน

## 2. ทางเลือกที่พิจารณา และเหตุผลที่เลือก Supabase

| ทางเลือก | ข้อดี | เหตุผลที่ไม่เลือก |
|---|---|---|
| Google Sheets + Apps Script | เปิดดู/แก้ในชีตได้ตรง ๆ ฟรี | ช้าเมื่อข้อมูลเยอะ ทำระบบสิทธิ์รายคนได้ยาก เขียนพร้อมกันหลายคนแล้วชนกัน |
| Firebase | เรียลไทม์ดี ฟรีเทียร์ใหญ่ | เป็น NoSQL ทำรายงานสรุป/รวมยอดยุ่งกว่า ย้ายออกยาก |
| เซิร์ฟเวอร์เองบน NAS | ควบคุมข้อมูลเต็มที่ | ต้องเปิดเครื่องตลอด ต้องเปิดพอร์ต ทำ HTTPS เอง และมีงานดูแลต่อเนื่อง |
| **Supabase (เลือกอันนี้)** | **PostgreSQL จริง + ระบบล็อกอิน + สิทธิ์ระดับแถว + เรียลไทม์ ครบในตัว ฟรีพอสำหรับ 4 คน** | — |

จุดตัดสินคือ **Row Level Security (RLS)**: กติกาว่าใครเห็นข้อมูลอะไรถูกบังคับที่ฐานข้อมูล
ไม่ใช่ที่โค้ดหน้าเว็บ ต่อให้มีคนแกะโค้ดฝั่งเบราว์เซอร์ก็ยังดึงข้อมูลบ้านอื่นไม่ได้
และเพราะเป็น PostgreSQL มาตรฐาน ถ้าวันหนึ่งอยากย้ายไปที่อื่นก็ `pg_dump` ออกได้เลย

## 3. สถาปัตยกรรม

```
   มือถือพ่อ        มือถือแม่        โน้ตบุ๊กลูก        แท็บเล็ต
       │                │                │                │
       └────────────────┴────────┬───────┴────────────────┘
                                 │  HTTPS
                   ┌─────────────▼──────────────┐
                   │  เว็บแอป (React + Vite)    │  ← โฮสต์ที่ Vercel/Netlify (สแตติกล้วน)
                   │  · แคชข้อมูลใน localStorage │
                   │  · คิวงานค้าง (outbox)      │
                   │  · Service Worker (PWA)     │
                   └─────────────┬──────────────┘
                                 │  supabase-js (REST + WebSocket)
                   ┌─────────────▼──────────────┐
                   │        Supabase             │
                   │  ├ Auth (อีเมล+รหัสผ่าน)    │
                   │  ├ PostgreSQL + RLS         │
                   │  └ Realtime (แจ้งเปลี่ยนแปลง)│
                   └────────────────────────────┘
```

ไม่มีเซิร์ฟเวอร์ที่เราต้องเขียนเองเลย — หน้าเว็บเป็นไฟล์สแตติก คุยกับ Supabase ตรง ๆ
กติกาความปลอดภัยทั้งหมดอยู่ในฐานข้อมูล

## 4. โครงสร้างข้อมูล

```
households ──┬── household_members (ใคร อยู่บ้านไหน ชื่อเล่นอะไร บทบาทอะไร)
             ├── household_invites  (รหัสเชิญ ใช้ครั้งเดียว อายุ 7 วัน)
             ├── accounts           (กระเป๋าเงิน: เงินสด / ธนาคาร / วอลเล็ท / บัตรเครดิต)
             ├── categories         (หมวดรายรับ-รายจ่าย พร้อมไอคอนและสี)
             ├── transactions       (รายการรับ-จ่าย-โอน ← ตารางหลัก)
             └── budgets            (งบประมาณต่อหมวดต่อเดือน)
```

**ตาราง `transactions`** เป็นหัวใจ เก็บทั้งสามประเภทในตารางเดียวโดยแยกด้วยคอลัมน์ `type`

| type | account_id | to_account_id | category_id | ความหมาย |
|---|---|---|---|---|
| `income` | กระเป๋าที่เงินเข้า | ต้องว่าง | ต้องมี | รายรับ |
| `expense` | กระเป๋าที่จ่ายออก | ต้องว่าง | ต้องมี | รายจ่าย |
| `transfer` | กระเป๋าต้นทาง | กระเป๋าปลายทาง | ต้องว่าง | โอนระหว่างกระเป๋า ไม่นับเป็นรับหรือจ่าย |

กติกานี้บังคับด้วย `CHECK constraint` ในฐานข้อมูล ไม่ใช่แค่ตรวจในหน้าเว็บ
ทำให้ข้อมูลเสียรูปไม่ได้แม้จะเขียนเข้ามาจากช่องทางอื่น

**ทำไมแยก `paid_by` กับ `created_by`:** `created_by` คือคนกดบันทึก ส่วน `paid_by` คือรายการนี้เป็นของใคร
แม่บันทึกค่าขนมให้ลูกได้ โดยรายงาน "ใครใช้เท่าไหร่" ยังนับให้ถูกคน และเว้นว่างไว้ได้ถ้าเป็นค่าใช้จ่ายส่วนกลาง

**ยอดคงเหลือไม่ได้เก็บเป็นตัวเลข** แต่คำนวณจาก `ยอดยกมา + รายรับ − รายจ่าย − โอนออก + โอนเข้า`
เพราะยอดที่เก็บไว้จะเพี้ยนทันทีที่มีใครแก้รายการย้อนหลัง คำนวณสดจึงถูกเสมอ
มี view `v_account_balances` ให้ใช้ฝั่งฐานข้อมูล และคำนวณซ้ำฝั่งแอปเพื่อให้ใช้ออฟไลน์ได้

## 5. ความปลอดภัย

1. **ล็อกอินด้วยอีเมล + รหัสผ่าน** ผ่าน Supabase Auth (เก็บรหัสผ่านแบบแฮช ไม่ผ่านมือเรา)
2. **RLS เปิดทุกตาราง** ทุก query ถูกกรองด้วย `is_household_member(household_id)` โดยอัตโนมัติ
   ผู้ใช้ที่ล็อกอินแล้วยังเห็นได้เฉพาะบ้านที่ตัวเองเป็นสมาชิก
3. **ฟังก์ชันตรวจสิทธิ์เป็น `security definer`** เพื่อตัดปัญหา policy เรียกตัวเองวนซ้ำ (infinite recursion)
   ซึ่งเป็นกับดักคลาสสิกของ RLS แบบตารางสมาชิก
4. **การเข้าบ้านทำผ่านรหัสเชิญเท่านั้น** (`join_household`) รหัสใช้ได้ครั้งเดียวและหมดอายุใน 7 วัน
   ไม่มีทางเดาเลข `household_id` แล้วเข้ามาเองได้
5. **คีย์ที่ฝังในหน้าเว็บคือ anon key** ซึ่งออกแบบมาให้เปิดเผยได้ อำนาจจริงมาจาก RLS + โทเคนของผู้ใช้
   ห้ามนำ `service_role` key มาใส่ในแอปเด็ดขาด
6. **สิทธิ์แบ่งสองระดับ:** เจ้าบ้าน (owner) แก้ชื่อบ้านและลบสมาชิกได้ สมาชิกทั่วไปบันทึก/แก้รายการได้ทุกอย่าง
   (ในบ้านเดียวกันเชื่อใจกันอยู่แล้ว จึงไม่ทำสิทธิ์ละเอียดกว่านี้ให้ใช้ยาก)

## 6. การซิงก์และการทำงานออฟไลน์

โจทย์ "ใช้ได้ทุกที่" หมายรวมถึงตอนอยู่ในตลาดที่สัญญาณไม่ดีด้วย แอปจึงออกแบบเป็น **offline-first**

```
กดบันทึก
   │
   ├─► อัปเดตหน้าจอทันที (optimistic update)  ─► ผู้ใช้เห็นผลใน ~0 วินาที
   ├─► เขียนลง localStorage                   ─► ปิดแอป/รีเฟรชแล้วข้อมูลยังอยู่
   └─► ต่อคิวใน outbox ─► มีเน็ต? ─ ใช่ ─► ส่งขึ้น Supabase ─► ลบออกจากคิว
                            └── ไม่ ─► รอ event 'online' แล้วส่งใหม่อัตโนมัติ
```

รายละเอียดที่สำคัญ:
- **สร้าง UUID ที่ฝั่งเครื่อง** ตั้งแต่ตอนกดบันทึก ทำให้ส่งซ้ำได้โดยไม่เกิดรายการซ้ำ (ใช้ `upsert`)
  และแก้/ลบรายการที่ยังไม่ทันส่งขึ้นคลาวด์ได้
- **คิวส่งตามลำดับ** ถ้างานหนึ่งติดเพราะเน็ต จะหยุดรอทั้งคิว แต่ถ้าติดเพราะข้อมูลผิดกติกา
  จะข้ามงานนั้นไปพร้อมเขียน log ไม่ให้คิวตันถาวร
- **Realtime** สมัครฟังการเปลี่ยนแปลงของบ้านตัวเอง พอพ่อบันทึกที่ร้านกาแฟ หน้าจอแม่ที่บ้านอัปเดตเอง
- **ซิงก์ซ้ำตอนกลับมาเปิดแอป** (`visibilitychange`) เผื่อ WebSocket หลุดตอนหน้าจอดับ
- **Service Worker** แคชตัวแอปไว้ เปิดใช้ได้แม้ไม่มีเน็ตเลย (แต่ไม่แคชคำขอไป Supabase — ข้อมูลต้องสดเสมอ)
- แถบสถานะบนหัวจอบอกตลอดว่า "ซิงก์แล้ว / รอส่ง N / ออฟไลน์" ผู้ใช้จะได้รู้ว่าข้อมูลถึงคลาวด์หรือยัง

**การชนกันของข้อมูล** ใช้กติกา last-write-wins ตามเวลาที่ส่งถึงเซิร์ฟเวอร์
สำหรับบ้าน 4 คนที่แทบไม่มีทางแก้รายการเดียวกันพร้อมกัน กติกานี้เพียงพอและเข้าใจง่ายที่สุด

## 7. การออกแบบหน้าจอ

ออกแบบแบบ **mobile-first** เพราะการบันทึกส่วนใหญ่เกิดตอนอยู่นอกบ้านบนมือถือ

| หน้า | ตอบคำถามว่า |
|---|---|
| **ภาพรวม** | ตอนนี้มีเงินเท่าไหร่ เดือนนี้รับ-จ่ายไปเท่าไหร่ หมดกับหมวดไหน งบเกินหรือยัง |
| **รายการ** | รายการเดือนนี้มีอะไรบ้าง (กรองตามประเภท/หมวด/กระเป๋า/คน และค้นหาจากบันทึกช่วยจำ) |
| **รายงาน** | แนวโน้ม 3/6/12 เดือน เฉลี่ยเดือนละเท่าไหร่ ใครใช้เท่าไหร่ |
| **ตั้งค่า** | จัดการกระเป๋าเงิน หมวดหมู่ งบประมาณ สมาชิก และส่งออก CSV |

ทางลัดที่ช่วยให้บันทึกเร็ว:
- ปุ่ม **+** ลอยอยู่ทุกหน้า กดแล้วเคอร์เซอร์เด้งเข้าช่องจำนวนเงินทันที
- ช่องจำนวนเงินคำนวณให้ พิมพ์ `120+35` ได้เลยไม่ต้องกดเครื่องคิดเลข
- หมวดหมู่เป็นปุ่มกลม ๆ กดครั้งเดียว ไม่ต้องเลื่อน dropdown
- ค่าตั้งต้นคือ "รายจ่าย วันนี้ กระเป๋าแรก ตัวเราเอง" ซึ่งเป็นกรณีที่เจอบ่อยที่สุด
- แตะรายการเดิมเพื่อแก้หรือลบได้ทันที
- รองรับโหมดมืดอัตโนมัติตามเครื่อง

## 8. ต้นทุนและการขยาย

- Supabase ฟรีเทียร์: ฐานข้อมูล 500 MB, ผู้ใช้ 50,000 คน/เดือน, Realtime 200 การเชื่อมต่อพร้อมกัน
- ประเมินการใช้จริง: 4 คน × 20 รายการ/วัน ≈ 29,000 แถว/ปี ≈ 3 MB/ปี → ใช้ได้หลายสิบปีบนแพ็กเกจฟรี
- ข้อควรรู้: โปรเจกต์ฟรีของ Supabase จะถูกพักถ้าไม่มีการใช้งานเลย 7 วัน (กดปลุกคืนได้จาก dashboard)
  ซึ่งไม่เป็นปัญหาถ้าใช้เป็นประจำ
- โฮสต์หน้าเว็บ: Vercel / Netlify / Cloudflare Pages ฟรีทั้งหมดสำหรับงานขนาดนี้

## 9. สิ่งที่ต่อยอดได้

เรียงตามความคุ้มค่าต่อแรงที่ลง:
1. **รายการประจำ** (ค่าน้ำ ค่าไฟ ค่าเน็ต) — เพิ่มตาราง `recurring_rules` แล้วให้แอปเสนอบันทึกอัตโนมัติเมื่อถึงกำหนด
2. **แนบรูปสลิป** — ใช้ Supabase Storage เพิ่มคอลัมน์ `receipt_path` ใน `transactions`
3. **เตือนเมื่อใกล้เกินงบ** — Web Push ผ่าน Service Worker ที่มีอยู่แล้ว
4. **เป้าหมายการออม** — ตาราง `goals` ผูกกับกระเป๋าเงิน
5. **สรุปส่งเข้า LINE ทุกสิ้นเดือน** — Supabase Edge Function + LINE Notify
6. **แยกหนี้กันเองในบ้าน** (ใครออกก่อน ใครต้องคืนเท่าไหร่) — ต่อยอดจาก `paid_by` ที่มีอยู่แล้ว

## 10. การสำรองข้อมูล

- **อัตโนมัติ:** Supabase สำรองรายวันให้ (แพ็กเกจฟรีเก็บย้อนหลังจำกัด)
- **ด้วยตัวเอง:** กด "ส่งออกข้อมูลเป็น CSV" ในหน้าตั้งค่าเดือนละครั้ง เก็บไว้ใน Google Drive
- **แบบเต็ม:** `pg_dump` จาก connection string ในหน้า Project Settings → Database
